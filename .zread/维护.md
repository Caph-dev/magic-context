## 同步上游

在仓库根目录执行：

```bash
git fetch upstream
git checkout master && git merge --ff-only upstream/master
git checkout notes && git rebase master
git push --force-with-lease origin notes
```

1. `git fetch upstream` 只更新上游引用，不改工作区。
2. `master` 用快进合并对齐 `upstream/master`。不能快进时先停下来，说明 `master` 上有不该存在的个人提交。
3. `notes` 变基到新的 `master` 上，笔记仍在最上面。变基会改写 `notes` 的提交哈希。
4. `--force-with-lease` 把改写后的 `notes` 推到 fork。远端 `notes` 若被别处更新，推送会拒绝，先拉取再处理。

`origin/master` 可以停在 fork 创建时的上游提交。阅读和同步以 `upstream/master` 与本地 `notes` 为准。若要让 fork 的默认分支也跟上上游，在快进 `master` 之后另执行 `git push origin master`。这只更新自己的 fork。

推送 `notes` 时，GitHub 可能给出 `https://github.com/Caph-dev/magic-context/pull/new/notes`。那是在自己的 fork 里比较分支，不会发到原项目。不需要打开。

## 变基冲突

冲突在 `.zread/`：保留自己的笔记内容，解决后继续。

```bash
git add .zread
git rebase --continue
```

冲突在 `.zread/` 以外：先停止，看清是哪一侧改了同一处。个人提交应只动 `.zread/`。

要放弃这次变基、回到变基前的 `notes`：

```bash
git rebase --abort
```

## 推送边界

- 在 `notes` 上执行 `git push`，目标是 `origin/notes`。
- 在 `master` 上执行 `git push`，目标是 `upstream`，因 push URL 为 `DISABLED` 会失败。
- 更新已变基的 `notes` 时使用 `git push --force-with-lease origin notes`。
- 不向 `cortexkit/magic-context` 推送，也不开指向原仓库的 pull request。

确认当前布局：

```bash
git remote -v
git status -sb
git log -1 --oneline master
git log -1 --oneline notes
```

期望：当前分支是 `notes`，`master` 与 `upstream/master` 指向同一提交，`notes` 比 `master` 多出个人提交。
